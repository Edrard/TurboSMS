# Логування PSR-3

`Api` і `Webhook` приймають будь-який `Psr\Log\LoggerInterface` та реалізують
`Psr\Log\LoggerAwareInterface`. Це дозволяє використовувати наявний логер
застосунку, зокрема Monolog. PSR-3 визначає інтерфейс логування, а PSR-4
залишається схемою автозавантаження класів бібліотеки.

## Підключення наявного логера

```php
use edrard\Turbosms\Api;
use edrard\Turbosms\Webhook;

// $logger — налаштований у твоїй програмі Psr\Log\LoggerInterface.
$api = new Api($config, null, $logger);
$webhook = new Webhook(getenv('TURBOSMS_WEBHOOK_SECRET'), 1048576, $logger);
```

У `Api` другий аргумент, як і раніше, є HTTP-клієнтом Guzzle. Логер передається
третім аргументом; `null` залишає стандартний HTTP-клієнт. У `Webhook` другий
аргумент залишається межею розміру тіла, третій — логером.

Можна використати стандартний `setLogger()` після створення:

```php
$api = new Api($config);
$api->setLogger($logger);

$webhook = new Webhook(getenv('TURBOSMS_WEBHOOK_SECRET'));
$webhook->setLogger($logger);
```

Старі конструктори та виклики не потребують змін. Без переданого логера
використовується `Psr\Log\NullLogger`: бібліотека не створює файлів логів,
не пише у stdout/stderr і не обирає зовнішній сервіс збору журналів.
Напрямок, формат, ротацію та зберігання налаштовує реалізація логера.

## Приклад із Monolog

Monolog — необов'язкова залежність твого застосунку, він не встановлюється
бібліотекою TurboSMS. Якщо використовуєш його, підключення може виглядати так:

```php
use Monolog\Handler\StreamHandler;
use Monolog\Logger;

// Визнач цей шлях у конфігурації своєї програми, поза публічною директорією сайту.
$logPath = getenv('TURBOSMS_LOG_PATH');
if (!is_string($logPath) || $logPath === '') {
    throw new \RuntimeException('Configure TURBOSMS_LOG_PATH.');
}
$logger = new Logger('turbosms');
$logger->pushHandler(new StreamHandler($logPath, Logger::INFO));
$api->setLogger($logger);
$webhook->setLogger($logger);
```

Поріг `INFO` включає завершення та помилки, але пропускає записи початку рівня
`DEBUG`. Для подробиць увімкни `DEBUG` на стороні свого логера. Бібліотека
передає однаково обмежені метадані на всіх рівнях: debug не розкриває тіло запиту.

## Які операції журналюються

| `operation` | Виклик |
| --- | --- |
| `message.send` | `sendMessage()` для SMS, Viber або гібридного повідомлення |
| `message.status` | `getMessageStatus()` |
| `user.balance` | `getBalance()` |
| `webhook.parse` | `parse()` для JSON або сирої URL-encoded форми |
| `webhook.parse_form` | `parseForm()` для готової PHP-форми |
| `webhook.handle` | Повна обробка через `handle()`, включно зі споживачем |

На один виклик записуються початок і один кінцевий результат.
`handle()` не створює вкладені записи про власний внутрішній парсинг.
Лог про успішний `parse()` означає лише перевірку й розбір даних, а не їх
збереження. Успіх `handle()` журналюється після успішного завершення споживача.
Конструктори, `changeConfig()` та окремі виклики `Message::validate()` не
журналюються цим механізмом.

## Рівні та поля

| Рівень | Подія |
| --- | --- |
| `debug` | Початок операції |
| `info` | Успішне завершення |
| `warning` | Часткові API-помилки, некоректні вхідні параметри, неправильний підпис або непідтриманий тип вебхука |
| `notice` | Повторний запит із кодом API `507` |
| `error` | Відмова API, збій транспорту, некоректна відповідь або помилка споживача вебхука |

Повідомлення фіксовані: `TurboSMS operation started.`, `TurboSMS operation
completed.` або `TurboSMS operation failed.`. Змінні дані передаються окремим
PSR-3 context, лише з цього набору:

| Поле | Значення |
| --- | --- |
| `operation` | Одне з імен операцій вище |
| `request_id` | Локальний ID для зв'язування початку та завершення одного виклику |
| `duration_ms` | Невід'ємна тривалість операції в мілісекундах; для `handle()` включає споживача |
| `http_status` | HTTP-код, якщо відповідь на вихідний запит отримана |
| `response_code` | Загальний числовий код API, коли відомий |
| `error_count` | Кількість API-помилок окремих рядків, якщо є результат API |
| `delivery_count` | Кількість звітів у розібраному вебхуку |
| `event_type` | Перевірений підтриманий тип вебхука |
| `error_type` | Обмежена категорія помилки без її сирого тексту |

`request_id` не є `sequence_id`, ID повідомлення або ID події TurboSMS. Він
створюється заново для кожного локального виклику, зокрема повторного.
Його не використовують для авторизації чи захисту від дублювання.
Тривалість вимірюється без запису початкового й кінцевого логів.

Категорії `error_type`: `api_error`, `duplicate_request`, `transport_error`,
`invalid_response`, `invalid_input`, `authentication_failed`, `unsupported_event`
та `processing_error`. Невдала доставка на кшталт `Expired` у результаті
успішного запиту статусу не стає помилкою отримання даних у журналі.

## Які дані не передаються логеру

Бібліотека не передає токени, секрет вебхука, підпис, заголовки, URL, тексти,
відправників, номери одержувачів, баланс, `sequence_id`, ID подій/повідомлень,
сирі відповіді та об'єкти винятків. Навіть текст `response_status` не
копіюється до журналу. Це стосується також URL зображень із параметрами доступу.

Замість логування всього об'єкта винятку записується безпечна категорія та
відомий числовий код. Початковий виняток продовжує надходити застосунку;
його логування самим застосунком — окреме рішення. Сторонні middleware,
процесори логера й код програми можуть записувати інші дані незалежно від SDK.

## Якщо сам логер зламався

Виняток або `Error` під час виклику логера перехоплюється й не змінює
результат основної операції. Успішне надсилання не перетворюється на помилку,
а збережений вебхук не втрачає можливість підтвердження через збій журналювання.
Початкова помилка API/споживача також не замінюється помилкою логера.
SDK не робить додаткових запитів чи спроб надсилання через помилки логування.

Доступність журналів контролюй засобами свого логера. Для вимкнення логування
без зміни об'єкта можна встановити стандартний NullLogger:

```php
$api->setLogger(new \Psr\Log\NullLogger());
$webhook->setLogger(new \Psr\Log\NullLogger());
```

## Сумісність і тести

Підтримані `psr/log` 1.x, 2.x і 3.x. Composer обирає версію відповідно до
PHP та інших залежностей застосунку. Для локального мінімального PHP 7.2.5
lock бібліотеки використовує 1.1.4; 2.x/3.x перевіряються на PHP 8.4.
PSR-4 namespace `edrard\Turbosms\` та способи надсилання збережені.

`composer test` перевіряє рівні, метадані, відсутність приватних даних,
заміну логера та збої журналювання. Використовується логер у пам'яті без
створення реальних журналів або звернень до TurboSMS.

Стандарт: [PSR-3 Logger Interface](https://www.php-fig.org/psr/psr-3/).
