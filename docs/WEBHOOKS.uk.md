# Вебхуки TurboSMS: отримання статусів доставки

Бібліотека має окремий клас `edrard\Turbosms\Webhook`. Він приймає подію,
перевіряє її підпис і структуру та повертає нормалізовані звіти про доставку.
Для цього не потрібні об'єкт `Api`, API-токен або запит до TurboSMS.
Наявні методи надсилання, `getMessageStatus()` і `getBalance()` не змінені.

Клас також підтримує [логування PSR-3](LOGGING.uk.md). Логер можна передати
третім аргументом конструктора або встановити через `setLogger()`. Успішний
лог `webhook.parse` означає розбір, а `webhook.handle` — також завершення
споживача. Підпис, секрет і дані звітів не копіюються в журнали.

## Налаштування в кабінеті

У розділі вебхуків TurboSMS створи callback із публічною HTTPS-адресою свого
endpoint. Вибери події `DLR_SMS_API` і `DLR_VIBER_API`, задай окремий секрет
вебхука та формат JSON. FORM DATA також підтримується, але для списків звітів
JSON усуває залежність від обмежень PHP на кількість полів форми.
За потреби увімкни HTTP Basic authentication і налаштуй ті самі облікові дані
на своєму endpoint.

Секрет вебхука не є API-токеном. Збережи його локально в конфігурації програми
або змінній середовища `TURBOSMS_WEBHOOK_SECRET`; не вставляй у Git, URL чи логи.
Налаштування кабінету й публікацію endpoint бібліотека не виконує автоматично.

## Формати запиту

Один POST-запит містить один конверт події:

| Поле | Призначення |
| --- | --- |
| `id` | ID події; це окремий ідентифікатор, не `message_id` |
| `signature` | Підпис, який перевіряє парсер |
| `type` | `DLR_SMS_API` або `DLR_VIBER_API` |
| `date` | Дата й час події |
| `try` | Номер спроби доставки callback, від 1 |
| `data` | Один об'єкт звіту або непорожній список звітів |

Для JSON передай сире тіло. Тип вмісту може містити параметр кодування:

```php
use edrard\Turbosms\Webhook;

$webhook = new Webhook(getenv('TURBOSMS_WEBHOOK_SECRET'));
$event = $webhook->parse($rawBody, 'application/json; charset=utf-8');
```

Для `application/x-www-form-urlencoded` передай сире тіло в той самий метод:

```php
$event = $webhook->parse($rawBody, 'application/x-www-form-urlencoded');
```

Для multipart FORM DATA використовуй вже розібраний PHP масив:

```php
$event = $webhook->parseForm($_POST);
```

У формах `data` може бути вкладеним масивом PHP або JSON-рядком. Поле `try`
у формі допускає десятковий рядок, який перетворюється на ціле число без
переповнення. У JSON очікується ціле число. ID події може бути рядком або
цілим числом; результат завжди містить рядок зі збереженням значущих цифр.

Парсер обмежує тіло 1 MiB, перевіряє дати та всі звіти до початку обробки.
Іншу межу можна передати другим аргументом `new Webhook($secret, $maxBytes)`.
Для форм також перевіряються вкладеність і кількість вхідних змінних; біля
межі `max_input_vars` запит відхиляється, щоб не підтвердити обрізаний пакет.
У вебсервері та PHP узгодь `post_max_size`, `max_input_vars` й обмеження тіла.
Для multipart PHP розбирає дані до виклику бібліотеки — для великих подій
використовуй JSON або JSON-поле `data`, а не сотні вкладених полів форми.

## Перевірка підпису

Використовується саме схема TurboSMS: `sha1($secret . $id)` із порівнянням
через `hash_equals()`. Це не HMAC, і до обчислення не додається тіло запиту.
Невідповідний або відсутній підпис спричиняє `WebhookAuthenticationException`;
callback споживача при цьому не викликається.

Схема підтверджує відповідність секрету та ID, але **не підписує поля статусу
чи все тіло**. Не вважай її гарантією незмінності отриманих даних або захистом
від повтору вже підписаної події. Використовуй HTTPS, за можливості додаткову
HTTP Basic authentication і перевірку прив'язки `message_id` у своїй системі.
Для звірки сумнівного стану є `getMessageStatus()`. Секрет і верхньорівневий
підпис не включаються в нормалізований результат парсера.

## Результат парсера

Парсер повертає іншу структуру, ніж вихідний HTTP API: тут немає `resp` / `error`,
оскільки це вхідна подія, а не відповідь на запит надсилання.

```php
foreach ($event['deliveries'] as $delivery) {
    $eventId = $event['id'];
    $messageId = $delivery['message_id'];
    $channel = $delivery['channel'];
    $state = $delivery['status'];
    $providerState = $delivery['raw_status'];
    $sentAt = $delivery['sent'];
    $updatedAt = $delivery['updated'];
    $operatorCode = $delivery['error_code'];
    $originalRow = $delivery['data'];
}
```

| Ключ | Що містить |
| --- | --- |
| `id`, `type`, `date`, `try` | Дані події; `try` — ціле число |
| `deliveries` | Список нормалізованих звітів |
| `message_id` | ID з відповіді надсилання, за яким слід знайти повідомлення |
| `channel` | Для SMS-події — `sms`; для Viber-події — фактичний `sms` або `viber` |
| `status` | Стан у термінах, сумісних із читанням статусу через API |
| `raw_status` | Оригінальний код TurboSMS |
| `sent`, `updated` | `sent_date` і `dlr_date`; `sent` також допускає `null` |
| `error_code` | Код оператора/Viber без перетворення: рядок, ціле число або `null` |
| `data` | Початковий рядок звіту з додатковими полями |

Мапінг станів:

| Код callback | Нормалізований стан |
| --- | --- |
| `DELIVRD` | `Delivered` |
| `READ` | `Read` |
| `EXPIRED` | `Expired` |
| `UNDELIV` | `Undelivered` |
| `REJECTD` | `Rejected` |
| Новий допустимий код | `Unknown`; початкове значення зберігається в `raw_status` |

Рядки часу залишаються без перетворення. Для `sent_date` і `dlr_date` сервіс
вказує київський часовий пояс. Парсер перевіряє формат, календарну дату та межі
годин/хвилин/секунд без використання системної бази часових поясів і без
визначення UTC-зсуву. Код помилки `'000'` не перетворюється на `0`:
значення оператора з початковими нулями залишаються доступними.

Для гібридної доставки враховуй `channel`: Viber-подія може повідомляти про
резервне SMS. При оновленні станів доцільно розрізняти пару
`message_id + channel`, щоб недоставка Viber не затерла успішне SMS.

## Обробка, підтвердження та повтори

Метод `handle($body, $consumer, $contentType)` викликає споживача один раз для
всього нормалізованого конверта й повертає рядок `OK` лише після його успіху.
Він не змінює HTTP-код і не виводить тіло відповіді самостійно.

```php
// $persistEvent — твій callable: атомарно зберігає подію/чергу за унікальним id.
$ack = $webhook->handle($rawBody, $persistEvent, 'application/json');
http_response_code(200);
echo $ack;
```

Якщо споживач викинув виняток, бібліотека не перехоплює його та не повертає
підтвердження. Підтверджуй callback після завершення транзакції або надійного
запису в чергу. Не відправляй `200` завчасно лише тому, що JSON успішно розібраний.

Вебхуки можуть надходити повторно. Задай унікальність за **ID події**, а не за
ID повідомлення: для одного повідомлення можуть бути різні події доставки та
прочитання. Парсер не веде власного сховища й не відкидає повтори мовчки;
ідемпотентність забезпечує споживач. Уже надійно збережений дублікат також
можна підтвердити `200`.

Не покладайся на порядок HTTP-запитів. Зберігай час звіту, стан та канал,
застосовуй правила переходів стану своєї програми; `try` — номер повтору
певної події, а не глобальна версія повідомлення. У разі неоднозначного порядку
звіряй поточний стан через API, не надсилай повідомлення повторно.

За правилами сервісу успіхом callback є HTTP `200`; інші коди викликають
повторні спроби. Отже, навіть `204` або `202` тут не замінюють `200`.
Тимчасовий збій збереження має повертати помилку, а не втрачати подію.

## Готовий приклад endpoint зі сховищем

[docs/webhook-endpoint.php](webhook-endpoint.php) — робочий приклад для PHP
із розширенням PDO SQLite. Для локального використання скопіюй його до
`examples/webhook.php`. Папка `examples/` ігнорується Git; після чистого checkout
створи її та скопіюй endpoint із `docs/` перед запуском інтеграційного тесту.
Він:

- приймає лише POST, перевіряє підпис, формат і розмір;
- підтримує необов'язкову HTTP Basic authentication;
- нормалізує JSON, URL-encoded і multipart форми;
- атомарно зберігає подію у SQLite-таблицю `turbosms_webhook_inbox`;
- підтверджує вже збережені дублікати без нового рядка;
- повертає `200 OK` після запису та `503` при збої конфігурації/сховища;
- не повертає клієнту винятки, секрети чи сирі діагностичні дані.

Потрібні змінні середовища:

| Змінна | Призначення |
| --- | --- |
| `TURBOSMS_WEBHOOK_SECRET` | Той самий окремий секрет, що в налаштуваннях webhook |
| `TURBOSMS_WEBHOOK_DB` | Абсолютний шлях до SQLite-файла поза публічною директорією сайту |
| `TURBOSMS_WEBHOOK_USER` / `TURBOSMS_WEBHOOK_PASSWORD` | Обидві разом для додаткової Basic authentication або обидві відсутні |

Каталог для SQLite має існувати та бути доступним на запис обліковці PHP.
Не розміщуй базу у web root і не додавай її до Git. При FastCGI переконайся,
що вебсервер передає HTTP Basic authentication до `PHP_AUTH_USER` / `PHP_AUTH_PW`.
У production вимкни виведення PHP-помилок у HTTP-відповідь.

Приклад уже приймає й надійно зберігає звіти. Застосування їх до таблиць
твоєї CRM/замовлень виконує твій worker: він читає `payload` з inbox і
зіставляє звіти зі збереженими `message_id`. Схему власної системи приклад
не припускає. Можна замінити SQLite на свій транзакційний споживач.

## Винятки

| Клас у `edrard\Turbosms\Exception` | Значення |
| --- | --- |
| `WebhookAuthenticationException` | Відсутній або неправильний підпис |
| `InvalidWebhookException` | Некоректний конверт, дані, формат або перевищення меж |
| `UnsupportedWebhookException` | Підпис правильний, але тип події не підтриманий; успадковує `InvalidWebhookException` |

Порожній секрет і неправильна конфігурація ліміту спричиняють звичайний
`InvalidArgumentException`. SQL, SOAP, SMPP, сесійні повідомлення Viber,
вхідні повідомлення та кліки тут не підтримуються. Вибирай у кабінеті лише
два підтримані HTTP API типи; помилки вибору подій не підтверджуються як успіх.

## Тести

`composer test` запускає перевірки парсера та всі попередні тести без мережі й
реальних токенів. Вони охоплюють підпис, формати, обидва канали, нормалізацію,
некоректні дані, пакетну атомарність перед викликом споживача й помилки обробки.

Окремий інтеграційний тест перевіряє справжній локальний HTTP endpoint та SQLite.
Він обмежений адресою `127.0.0.1` і використовує лише тестові значення.
Для відтворення запусти в окремому локальному процесі PHP-сервер із кореня
бібліотеки, задавши **лише для тестового процесу**:

```text
TURBOSMS_WEBHOOK_SECRET=endpoint-test-secret
TURBOSMS_WEBHOOK_USER=endpoint-test-user
TURBOSMS_WEBHOOK_PASSWORD=endpoint-test-password
TURBOSMS_WEBHOOK_DB=<абсолютний шлях до нового тимчасового SQLite-файла>
```

Це публічні тестові значення, не використовуй їх у production. За наявності
драйвера PDO SQLite команди мають такий вигляд:

```bash
php -d extension=pdo_sqlite -S 127.0.0.1:8087 -t .
php -d extension=pdo_sqlite tests/webhook-endpoint.php http://127.0.0.1:8087/examples/webhook.php ABSOLUTE_TEST_DB_PATH
```

Другу команду виконай в іншому терміналі з тим самим шляхом до ще не створеної
бази. Тест перевіряє HTTP-коди, обидва формати форм, збереження, дублікати та
відмову запису з подальшим відновленням. Після тесту зупини локальний сервер.
Справжні callbacks від TurboSMS не використовуються.

Правила сервісу: [офіційна документація вебхуків](https://turbosms.ua/en/callback.html).
